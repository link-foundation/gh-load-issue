The original issue, PRs #19 and #21, issue and PR timelines, conversation comments, inline review comments, submitted reviews, sub-issue response, run metadata and raw job logs are preserved here. The issue and pull request snapshots at the start of the investigation had no comments, submitted reviews or required sub-issues. The archive includes every historical run the Actions API returned before the fix.

## Findings and verification

| Requirement or symptom | Root cause | Implementation and verification |
| --- | --- | --- |
| Fix the main release failure | The runner selected Node 20.20.2 and npm 10.8.2. The floating npm upgrade selected an incompatible major and the wrapper accepted a failed process. npm 10 is below the minimum for GitHub trusted publishing. The historic log establishes enough to explain why OIDC was unavailable on that runner. The npm publisher’s current configuration is visible only to package maintainers. | Pin Node 24.22.3 with its bundled npm 11.19.1, fail before versioning if installation or version checks fail, and exercise the real GitHub identity and package exchange before release checks and mutations. Focused tests exercise runtime rejection, successful exchange and an actionable denial. [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/), [npm CLI engine requirements](https://github.com/npm/cli/blob/v11.19.1/package.json) |
| Detect failed and partial releases | Old versioning permanently consumed the changeset before registry acceptance, retried permanent errors and never verified exact version, latest tag, or the installed executable. | The verified version commit carries its triggering SHA. A rerun reuses the same commit only when it can verify the parent, version and trailer. Recovery publishes the checked current main version without incrementing again. npm errors distinguish permanent authorization failures, transient failures and version conflicts. After publication, anonymous registry checks require the version, latest tag and executable. A GitHub Release targets the checked commit and a mismatched existing tag fails. Tests exercise structured npm and GitHub failures. The disposable recovery experiment checks real Git history and both locks without registry writes. |
| Fix false rejection and false acceptance of changesets | The old validator counted all pending files and required exactly one. It also trusted a branch-name exemption. Docs and placeholder edits failed, while a changeset already in the base could satisfy a code change. | Validate added and modified files in the merge result using the Changesets parser, reject invalid package names or bump types, allow multiple entries, and exempt evidence, documentation and test-only changes from mandatory version bumps. Exercise a real Changesets bump and both lockfiles in package CI. |
| Make test failures visible | Broad catch blocks accepted GitHub errors, assertion failures and false error-path matches. Integration jobs lacked a token and the no-image test used an issue without a downloadable fixture. The suite aggregator repeated suites already discovered by Bun. | Run real GitHub integration with a read-only workflow token. Use a local fixture with a real PNG for image download and opt-out, and assert expected exit status and output for errors. Run once on each supported runner. The old anonymous failures appear in the main log around lines 501–548 and 800–804. |
| Eliminate released package warnings and verify the consumer path | npm normalized the relative `./` in the package launcher and historic testing did not guard every release path. | Declare the canonical bin path and install the packed artifact into an isolated consumer project. Invoke the installed binary with `--version` and `--help`. The release publishes the artifact that passed smoke testing, and verifies another installation from the public registry before publishing GitHub release notes. |
| Address CI warnings and hidden quality failures | The old actions targeted deprecated Node runtimes. npm dependency audits printed warnings in the middle of release installs without gating anything. jscpd's default 1000-line cap skipped the 1040-line CLI, and tests and release scripts were excluded. | Pin maintained action revisions, configure Git’s initial branch, remove the deprecated Secretlint preset, use audited npm and Bun lockfiles, and fail on audit findings at moderate or above. Match the source line limit across ESLint, the file-size check and duplication analysis. Run actionlint, ShellCheck, zizmor, Secretlint and documentation checks. [Node 20 runner deprecation](https://github.blog/changelog/2025-09-19-deprecation-of-node-20-on-github-actions-runners/) |
| Keep CI accurate across triggers | The previous workflow put unrelated PR checks behind the changeset job, skipped normal checks on manual dispatch, and offered release modes from arbitrary branches. | Test GitHub's synthetic PR merge commit, classify paths with a conservative default, and require all applicable CI jobs in a final gate. Run checks on ordinary PR opening, reopening, commit updates and ready-for-review. Cancel only superseded commit checks and serialize main publishing. Limit release modes to main and keep their credentials on release jobs. |
| Fix the manual Changeset PR mode | Description text was interpolated into shell code, formatting errors were ignored, and the implicit repository token cannot create PRs under the current repository settings. | Pass manual values through environment variables, fail on formatting problems, and create a draft through a repository-scoped `RELEASE_PR_TOKEN`. The current repository settings disable Actions creating PRs or approving reviews and the repository has no visible Actions secrets. A repository owner must provision that credential to verify real draft creation. A regular changeset PR remains available. |
| Compare every file and reuse relevant template practices | The downstream workflow was an older adaptation. Shared conventions had changed independently. | The complete union of paths and blob IDs appears in [the tree comparison](template-comparison.tsv), with the decisions below. The original upstream tree and retrieved practice guide are preserved alongside it. |
| Report a shared upstream problem and add diagnostics for unknowns | A package-scoped exchange alone cannot distinguish a publisher allowed to publish immediately from a staged-only publisher. npm dry-run skips the registry write and cannot prove that permission. | The shared template report includes reproducible cases, workarounds and code-level options. The release workflow and scripts support opt-in `verbose` and `RELEASE_DEBUG=1`; normal output names the failing operation without printing credentials. [Template issue #323](https://github.com/link-foundation/js-ai-driven-development-pipeline-template/issues/323), [npm trusted publishing settings](https://docs.npmjs.com/trusted-publishers/), [npm publish implementation](https://github.com/npm/cli/blob/v11.20.0/lib/commands/publish.js) |

The issue has no required child issues. | PR #21 implements and tracks the entire downstream repair and links the independent upstream report. Real npm publication and GitHub release creation require the trusted main workflow. |

## Template comparison and selected approach

The comparison uses downstream baseline `0d619ec` and template `8e72538d579d904aff818c2447fb3c2413d3a989`. It lists 582 unique file paths, with 23 different files in common, two identical files, 16 downstream-only paths and 541 template-only paths. The template includes eight workflow files and 79 pipeline scripts. [Pinned template tree](https://github.com/link-foundation/js-ai-driven-development-pipeline-template/tree/8e72538d579d904aff818c2447fb3c2413d3a989), [shared CI/CD guide](https://github.com/link-assistant/hive-mind/blob/main/docs/CI-CD-BEST-PRACTICES.md)

| Template area | Downstream decision |
| --- | --- |
| `release.yml`, versioning, package metadata, registry and release-note scripts | Adopt early planning, strict subprocess errors, Changesets, bounded retry, package preflight, exact artifact and registry proofs, and idempotent release notes. Keep one package and a single Bun runtime. Native Node APIs and installed Changesets avoid fetched helper code and extra release dependencies. The package already exists publicly, so the first-publication token path does not apply. |
| `workflows.yml`, shell and workflow checks, terminal status tracking | Apply actionlint, ShellCheck and zizmor, full action pinning, scoped permissions, explicit timeouts, and a required result for each applicable PR job. The release and draft-PR jobs run after the gate. The GitHub workflow still reports a failure if either job fails. |
| `security.yml`, dependency and secret scanners | Both committed lockfiles receive full dependency audits on each run and weekly. Secretlint scans Git's tracked inventory, including force-added evidence logs. Upstream CodeQL and dependency-review integration address separate source-analysis and GitHub dependency-graph concerns. The project uses ESLint for required source checks and full lockfile audits to cover existing and changed transitive dependencies. |
| `links.yml`, document and Lychee helpers | Validate size and key headings, then check repository links offline during PR checks. Test public destinations on the schedule. The npm web frontend returned 403 for automation while anonymous registry metadata confirmed the package, so the scheduled check verifies that URL's destination through the registry. |
| `rerun-unacquired.yml`, job budgets and runner utilities | Keep short, explicit job timeouts and separate PR supersession from serial publishing. No collected historical run failed to acquire a runner. CI retrying a runner outage is independent of the npm retry and recovery path. |
| `javascript-first-gate.yml`, `javascript-first-example.yml`, cross-language path/workspace tooling | The CLI is one JavaScript package with one dependency root. Its planner reuses the path classification and conservative full-suite fallback. No workspace or non-JavaScript build graph applies. |
| `example-app.yml`, Pages, preview, desktop, signing, native container and artifact helpers | The project ships an npm CLI. The pipeline has no site deploy, desktop/mobile build, Docker image, native build, multi-registry mirrors or archived evidence files requiring extraction. |
| Root configs, templates, tests, examples, experiments and reference docs | Compare all paths in the inventory. Keep the repository's public CLI interface and source requirements. Reuse existing Husky and lint-staged hooks, ESLint and Prettier, Bun tests, package fixtures, Changesets, and the release-specific checks above. Template fixtures for additional products and runtimes do not describe surfaces this project ships. |

The shared guide's 17 principles map to the implementation as follows.

| Guide principles | Application |
| --- | --- |
| 1, 5, 7 and 10 | Classify changes conservatively, test the GitHub merge result, run quick lint and release authorization before relevant slower jobs, and preserve ready/review runs separately from superseded commit runs. Current full suites are short enough to run on every relevant commit. A main advance after a checked release fails the explicit release SHA guard. GitHub branch protection and merge-queue settings are controlled by repository administrators. |
| 2, 3, 4 and 8 | Enforce 1100 lines, run Prettier and strict ESLint, check duplication, retain Husky and lint-staged. |
| 6 and 9 | Validate independent Changesets, synchronize both lockfiles, version on the default branch, verify the artifact, and make recovery idempotent. |
| 11, 12, 14 and 15 | Scan secrets, check documentation and workflows, and audit both committed lockfiles on PR and scheduled runs. |
| 13 | Applies to projects publishing multi-architecture container images. |
| 16 and 17 | Check npm runtime and package identity early, report denied credentials and externally imposed failures explicitly, and verify the publication anonymously. Tests separately exercise reproducible fixture failures and live GitHub connectivity. |

Keeping Changesets for versioning and using the official npm CLI for the single tested tarball is smaller than importing the template's generalized publisher. The Changesets action could manage version PRs, which would change this repository's automatic release model and require PR-creation credentials on every normal release. Using npm staged publishing is an option for maintainers who want approval before distribution, and it would require separate handling of pending and publicly published versions. The direct path preserves the existing release feature. [Changesets action](https://github.com/changesets/action), [GitHub pull request workflow events](https://docs.github.com/actions/using-workflows/events-that-trigger-workflows#pull_request), [related upstream issues](template-related-issues.jsonl)

## Reproduction

- Inspect the historical release failure with `gh run view 37561736761 --repo link-foundation/gh-load-issue --log`, or use the preserved log above. Compare the changeset-only failure in run 45953561496.
- Run `bun test tests/test-ci-release.test.mjs tests/test-npm-release.test.mjs` for publisher and release regressions and `bun test` for the full suite. The GitHub integration tests need read access to the public fixture using `GH_TOKEN` or an authenticated GitHub CLI.
- Run `bun run check` and `bun run test:package` for quality gates and the installed npm artifact.
- Run `bash experiments/reproduce-release-recovery.sh` from a checkout of this PR that still contains its pending changeset. It creates a disposable local remote, runs version creation, and confirms rerun and recovery select the same version commit. It never calls npm publish.
- To finish live production verification, the main workflow needs an npm trusted publisher for this repository and `release.yml` with the direct **npm publish** action enabled. The draft-Changeset PR route additionally needs the repository-scoped token described above. No registry or release writes take place in PR CI.
